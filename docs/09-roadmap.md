# 9. Roadmap (after 0.1)

Do not build these in 0.1. Keep the design open to them where noted.

## Soon after the initial release

Small gaps found while building 0.1 (added 2026-11-14). Pick these up first after 0.1 is live.

- **In-page camera for "Take photo" in the track chat (2e, 2f, 2j).** Today the button opens the device's file picker (`capture` attribute), which on a laptop doesn't show the camera. Add a camera view inside the chat, like the 0.2a popup, for photographing textbook pages. This can share its camera component with version 0.2.
- **Ask for the current password when a parent changes their email (5d).** Today the change needs only a code sent to the new address, as rules §1 say. Also asking for the current password would stop someone using a signed-in device left open from moving the account, and all sign-in codes, to their own email.
- **Exams open in full screen (4.1b, 4.2a–4.2c).** *(Added 2026-11-15, owner; **built in v0.3.1**, 2026-11-17.)* Pressing Start puts the exam paper in full screen by default, so the paper has the whole screen and the rest of the browser is out of sight, like sitting a real paper. The exam's top bar has a button to exit full screen and, once out, a button to go back into it; leaving with Esc works too. Notes for building it:
  - Browsers only allow full screen from a click, so the Start button (or Continue) must request it. If the browser refuses or doesn't support it (iPhone Safari, for example), the exam opens normally with no error.
  - Entering or leaving full screen changes the window size, so the pages are laid out again (rules §5); answers and the current question are kept, as on any resize.
  - Leaving full screen never leaves the exam, and "Leave exam" also exits full screen.
- **Record each sitting of an exam, for analytics (4.1b).** *(Added 2026-11-15, owner.)* Today an exam stores when it was first opened (`startedAt`), submitted (`submittedAt`) and marked (`markedAt`), and each answer stores when it was last saved. Leaving an exam and coming back works (answers are kept and `startedAt` doesn't change), but nothing records the leaving and returning. So `submittedAt − startedAt` counts breaks as exam time, and we can't tell a paper done in one go from one spread over three days. Add an exam sessions log: one row each time the learner opens or returns to the paper and when they leave it (Leave exam, tab closed or hidden, signed out), with the reason for leaving. From that, work out the active time and the number of sittings for each exam. Notes for building it:
  - Use the page's `visibilitychange` and `pagehide` events, sending with `navigator.sendBeacon` so the event still arrives when the tab closes. Close any session still open after a timeout, using the last answer save as its end time.
  - This is for analytics only in this step: no time limits, and nothing shown to learners or parents yet.
- **Show the parent's activity bar chart to students too (2k → 3c).** *(Added 2026-11-17, owner.)* The parent's Students page shows each child's practice as a small bar chart: exams and flashcard sessions per day for the last 7 days, plus the 26-week grid (`ActivityCharts` size `sm` in `src/app/(parent)/students/page.tsx`). Show the same chart to the learner as well. Today a learner sees the full-size version only on the Today tab of their dashboard, and only after their first exam or flashcard session; it isn't on Recent exams, All tracks, Your tracks or their profile. Settle first: which screens get it (all dashboard tabs, Your tracks, or the profile), and the small or full-size version. Same data and rules as the parent's chart (§9), so no new data is needed. *(**Built 2026-11-18**, owner chose: the full-size charts on Today from the first day, plus an overall scores chart for all exams on Recent exams; rules §9.)*
- **A question taller than the whole page.** The paper never scrolls (rules §5), but a single question taller than a full column can't be split or shrunk, so it overflows. This is very rare with questions of a word or one sentence. Fix it by asking the AI to keep prompts short (with a length check when questions are written), or by letting just that one question scroll inside its own box.

## Later versions

1. **Upload written answers** *(was called version 0.15 in the 0.1 brief)*. The student writes longer answers on paper and uploads photos or a PDF with the exam (screen 0.15a). *Plan for it:* answers can carry attachments; marking can be asynchronous.
2. **Camera capture** *(was called version 0.2 in the 0.1 brief; 0.2 is now two kinds of account, see `docs/plan-0.2.md`)*. The student photographs each answer page with the laptop camera, one page at a time, without leaving the exam (screen 0.2a).
3. **Ready-made packages.** Board and class packages (CBSE, ICSE) and add-on packs (general knowledge, coaching, AI) that load tracks automatically. Shown as Coming soon in 0.1 (2c).
4. **Create a track from Claude.** A connector so a parent talking to Claude about their child's studies can ask Claude to create an owlrnd track from that conversation. The parent confirms in owlrnd before it goes live. *Plan for it:* keep track creation as one internal operation that both the chat and an external caller can use.
5. **Several tracks at once.** From one chat or one connector request, propose one track per chapter or test from a term's syllabus or test timetable; the parent confirms them together.
6. **Flashcards.** *Built in 0.3 "Flashcards" (2026-11-16); see item 19 and `plan-0.3-flashcards.md`.* Missed questions and weak topics as flashcards between exams, grouped by track.
7. **Progress views.** A student progress page and a fuller parent profile with scores over time.
8. **owlrnd for college students.** *Now part of 0.2 as self-managed learners; see `11-editions.md` and `plan-0.2.md`.*
9. **A shared, self-improving question bank.** *(Added 2026-11-15, owner.)* Today every question is written for one track and used only there. Instead, keep every good question in one shared bank and reuse it for any student studying the same thing, writing new questions with the AI only when the bank has nothing suitable. This cuts the AI cost per exam (writing papers is most of the bill), makes papers appear instantly, and lets question quality improve with use. **Limit (terms of use, owner 2026-11-16):** exams and flashcards created from material a user uploaded are used only in the account it was uploaded to and are never shown to other users or reused (textbook copyright). So the shared bank may only hold questions not written from uploaded material, unless the terms change and users agree first.
   - **Describe each question richly.** Board and class, subject, a shared topic taxonomy (so "Ohm's law" in two families' tracks is the same topic), question type, the skill it tests (recall, apply, multi-step), the source it was written from (textbook, edition, chapter, when known), and a fingerprint of its wording to catch near-duplicates.
   - **Grade questions from real answers.** Every marked answer updates the question's statistics: how hard it really is (share answered correctly, adjusted for the strength of the students who met it, in the style of item response theory), how well it separates strong from weak students, and how often it is left blank. A question that strong students keep getting wrong is a sign of a bad answer key.
   - **Check quality before and after use.** New questions pass an AI review (one correct answer, plausible wrong options, suitable for the class) before entering the bank. Flags from parents or students, suspicious statistics, or a failed review take a question out of circulation for a person or the AI to look at.
   - **Choose questions to fit the child.** The exam plan (rules §4: weak topics, strong topics, retries) stays the same, but each slot is filled from the bank: the right topic and class, a difficulty matched to the child's current level on that topic, never a question they have seen recently, and a mix of question styles. Only gaps are written fresh, and those join the bank.
   - **Fit with ready-made packages (item 3).** A CBSE or ICSE package is a curated, pre-graded slice of the same bank.
   - **Privacy and rights to settle first.** Questions written from one family's uploaded pages would reach other families, so: the bank holds only questions, never the material or anything about the child; no names or personal details in questions (checked when they are written); decide what happens to shared questions when a family deletes their account; update the privacy policy and ask parents to agree; and check that reusing questions derived from copyrighted textbooks is allowed.
   - *Plan for it now:* keep writing topic names and question types consistently, store question statistics per question (not only per exam), and keep the AI-written explanation with each question.
10. **Report a wrong question or a wrong AI answer.** *(Added 2026-11-15, owner.)* On the marked paper (4.1f, 4.1g) and in exam history (2h), a student or parent can flag a question as wrong (unclear, more than one right answer, outside the track's topics, unsuitable for the class) or flag the AI's answer or marking as wrong (bad answer key, a correct written answer marked wrong). The reporter picks a reason and can add a short note. A flagged question is taken out of circulation until a person or the AI reviews it; if the marking was wrong, the student's score and points are corrected. *Plan for it:* keep the AI's answer key and explanation with each question, and keep marks re-calculable after an exam is submitted. With the shared question bank (item 9), these reports are the "flags from parents or students".
11. **Free credits for confirmed reports.** *(Added 2026-11-15, owner.)* A report from item 10 that is confirmed on review earns the reporter's family free credits. Depends on pricing and credits existing (0.1 has none). Settle first: how many credits per report, a cap per family per month, one reward per question (the first confirmed reporter), and who confirms (a person, the AI, or the AI with a person checking) so the reward can't be farmed.
12. **Advanced exam-readiness reporting.** *(Added 2026-11-15, owner.)* Data-science-level insight into how ready a child is for a real exam, going well beyond the progress views (item 7). For example: a predicted score and readiness per track with a confidence range; mastery per topic over time, including how quickly topics are forgotten and when to revisit them; where marks are lost (topic, question type, skill, blanks, time pressure); a comparison of pace against the date of the real exam; and plain-language recommendations for the parent on what to practise next. *Plan for it:* store every answer with its question, topic, skill, time taken and result (not only exam totals), so these models can be built later from history. Benchmarks against other students depend on the shared question bank (item 9) and need the same privacy decisions.
13. **Manual parent verification from the back office.** When usage grows, an admin queue of consent records where staff can check a parent (for example a short call or an ID check outside the product) and mark them verified, rejected or needing follow-up. *Plan for it:* consent records already store a verification level (see `11-editions.md` §2.4), so this only adds a staff screen and two new levels.
14. **Parent verification with DigiLocker.** Let the parent confirm they are an adult through DigiLocker or a similar government-authorised service, as the data protection rules describe. Use it if manual checks don't scale or legal advice says email alone isn't enough.
15. **Subjects: several tracks grouped into one.** *(Added 2026-11-15, owner.)* Let a learner (or a parent) group tracks into a subject, for example the chapters of JEE Physics, and see and practise the subject as a whole. The way tracks combine is not decided yet. It is also the likely basis for ready-made exam packages (item 3, and the JEE Main and NEET UG designs in screens sm-2a and sm-2b), which were taken out of 0.2.
16. **Exam rules settings.** *(Added 2026-11-15, owner.)* A settings option that controls how a track's exams work. Each ready-made package (item 3) carries its own predefined settings (for example JEE Main: +4 / −1 negative marking, multiple choice and numerical answers), and a learner or parent sets their own for a Build your own track. Settings cover rules such as negative marking, question types, exam size and time, and the goal. *Plan for it:* keep marking and scoring rules in one place that reads per-track settings, with today's 0.1 rules as the defaults.
17. **Analyse an outside exam paper.** *(Added 2026-11-15, owner.)* A learner or parent uploads a marked exam paper from school, coaching or a mock test (photos or a PDF of the paper with marks, or a marks sheet or teacher's comments) and asks owlrnd to analyse it. The AI reads the questions, the marks and any answers it can see, and maps each question to the track's topics, then compares the result with the learner's owlrnd history on the matching tracks to explain where and why marks were lost. For example: a topic the track never covered, a topic practised but only with easier or different question types, a skill the exams didn't test (multi-step working, long answers, numericals), or a topic the learner was strong on in owlrnd but still lost marks on (a sign the practice wasn't close enough to the real paper). It then proposes changes for the controlling account to confirm: topics to add or re-weight, question types and difficulty to add, and a focus for the next exams. Nothing changes until they confirm (rules §3: adding topics restarts a track that reached its goal). *Plan for it:* reuse the track chat's upload handling (photos, HEIC, PDFs); keep topic names consistent so outside questions can be matched to them; and store answers per question with topic, type and skill (as in item 12) so the comparison has history to work from. Related: upload written answers (item 1) and exam-readiness reporting (item 12). The AI limits still apply (AI §6): it works only from the uploaded paper and the track's topics and material, and the learner's own paper is private to their account.
18. **Hand a child's account over, or let a child manage their own tracks.** *(Parked from 0.2 by the owner, 2026-11-16; editions §2.5.)* A parent-managed child who grows up (for example 14 and preparing for JEE, or turning 18) keeps their history, tracks and points but takes control: their own email for codes, their own tracks, and the parent's view ends unless the child keeps it on. In 0.2 a parent-created account is always the parent's: codes go to the parent and the parent sets up the tracks. *Plan for it:* learners already have a type and a parent link (M7), so the change is mostly a flow (the child adds and verifies an email) and flipping the type; consent rules (M10) apply to under-18s.
19. **Flashcards: "Practise" next to Start.** *(Added 2026-11-16, owner; **built in 0.3 "Flashcards"** (F1–F4, 2026-11-16), see `plan-0.3-flashcards.md` and previews `screens/fc-*`.)* A second button under **Start** on each suggestion and track card, opening a quick flashcard session for that track: no paper, no marks, no effect on the goal. *Idea:* the AI writes cards (term or question on the front, answer and the one-line explanation on the back) from the track's topics and material, weighted the same way as exams (weak and untested topics first; missed exam questions come back as cards). The learner flips and says "Got it" or "Not yet"; "Not yet" cards return sooner (simple spaced repetition). Points could reward finishing a session lightly, without counting towards the goal. *Plan for it:* cards belong to the track like questions (and, per the terms, stay in the account whose material they came from); reuse the exam writer's topic plan and the AI limits; count card generation against the AI allowance. Until it's built, the button isn't shown, so learners don't meet a dead end.
20. **A separate tracker for flashcards.** *(Added 2026-11-16, owner.)* Flashcard practice gets its own progress view and streak, separate from exam streaks and points (0.3 keeps flashcards out of exam streaks). *Plan for it:* 0.3 already stores every session and review (`flashcard_sessions`, `flashcard_reviews`), so the tracker can be built from that history.

21. **Repetition mode for a completed track.** *(Added 2026-11-16, owner.)* On a track that reached its goal, the controlling account can choose **Repeat** instead of adding topics. The track goes back to `active` with the same topics and material, goal progress returns to 0, and exams start again, but the goal gets stricter with each repetition:
    - **First run** (today's track): the goal set when the track was created (default 8 / 10 in 3 exams in a row, rules §3).
    - **2nd repetition:** 9 / 10 or better in 3 exams in a row.
    - **3rd repetition:** 10 / 10 in 3 exams in a row.
    - **4th repetition and later:** every exam must be 10 / 10 (still 3 in a row).
    - The "every topic strong" coverage condition (rules §3) still applies in every repetition.
    - **Tag on the card.** Once a track is set to repeat, its suggestion and track cards (learner and parent views) show a tag such as **2nd repetition**, **3rd repetition** and so on. A track on its first run shows no tag.
    - Reaching the goal in a repetition stops the track again (`goal reached`), offering **Repeat** (next level) or **Add topics** as before. Adding topics (2j) starts a new first run with a new goal, so the tag is cleared.
    - *Plan for it:* store a repetition number on the track (1 = first run) and keep each run's exams in history with its number; keep the per-repetition thresholds in config (as with other goal defaults in `10-decisions.md`); exam writing follows rules §4 as usual, so a repeated track keeps targeting weak topics and avoids recently seen questions.
22. **Delete or archive any track.** *(Added 2026-11-16, owner; **built 2026-11-18**, rules §2.)* Today only a track that reached its goal can be archived, and there's no way back (`10-decisions.md` §2). Let the controlling account (the self-managed learner, or the parent for a child) tidy up their tracks at any time:
    - **Archive** any track, whatever its status (active, paused, goal reached). It leaves the learner's dashboard, suggestions and track lists, stops being offered for exams and flashcards, and keeps all its history. Archived tracks are listed under "Archived tracks", where they can be **restored** to the status they had before.
    - **Delete** a track permanently: its topics, material (uploaded photos and PDFs), exams, answers and flashcards are removed after a confirmation that names the track, and it cannot be undone. Points already earned stay with the learner, so their total and level don't drop.
    - An exam in progress on the track is discarded on archive or delete (with a warning in the confirmation).
    - Learners managed by a parent can't archive or delete; the permission policy (editions §2.3) already reserves track changes for the controlling account.
    - *Plan for it:* keep archive as a status with the previous status stored for restore; make delete one operation that removes the track's rows and its stored files together, so nothing is left behind in storage.
